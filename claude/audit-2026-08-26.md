## 🟠 Les défauts réels

### 1. `/tarifs` publie le vocabulaire que le site interdit

`npm run controle` remonte **13 affirmations** à chaque exécution. Trois familles sont de
vrais écarts, toutes dans `src/lib/tarifs.ts` :

| Ligne | Texte publié |
|---|---|
| `320` | `{ fonction: "Automatisations avancées", … }` |
| `321` | `{ fonction: "Intégrations standards", … }` |
| `323` | `{ fonction: "API", … }` |
| `340` | `DIFFERENCIATION.business` — « les automatisations métier », « les intégrations standards » |
| `342` | `DIFFERENCIATION.enterprise` — « l'API, les intégrations avancées, … les automatisations avancées » |
| `385` | `OPTIONS` — « API et intégrations » |

`API`, `intégration` et `automatiser` sont sur la liste des mots que le site refuse, tenue
sur les vingt pages. Ils sont pourtant rendus à l'écran sur `/tarifs`, dans le comparatif et
dans les promesses de plan — c'est-à-dire à l'endroit précis où, selon la règle du Lot 5,
**une ligne publiée est un engagement contractuel opposable**.

Deux issues, l'une ou l'autre, jamais rien :

- **soit** reformuler ces six lignes dans le vocabulaire du site (le comparatif dirait ce
  que le client obtient, pas le nom technique du moyen) ;
- **soit** inscrire dans `controle-editorial.mjs` une exemption **nommée et motivée** pour
  `tarifs.ts`, au motif que le comparatif contractuel emprunte le vocabulaire du contrat.

Ce qu'il ne faut pas faire, c'est laisser en l'état. Le projet a déjà établi la règle :
**un contrôle qui remonte des avertissements permanents ne sera plus jamais lu.**

⚠️ Le 14ᵉ signalement, `<Connecteur />` dans `ChainSection.tsx`, est un **faux positif** :
c'est un nom de composant React, jamais rendu comme texte. Le contrôle devrait ignorer les
identifiants de code, exactement comme il a appris à ignorer « affectée » pour `FEC`.

### 2. `SuiviErreursService` — dette n° 4 confirmée, et son test ment

`backend/src/common/logging/suivi-erreurs.service.ts` (et non `modules/suivi-erreurs/`,
l'énoncé du registre est imprécis) :

```
205-209   await this.email.sendCustomEmail({ … })      // valeur de retour ignorée
211-215   updateMany({ … data: { notifiee: true } })   // marquage inconditionnel
217-218   // commentaire : « Le mail n'est pas parti : les erreurs restent notifiee: false »
```

`sendCustomEmail` (`backend/src/modules/email/email.service.ts`) **ne lève jamais** :
quatre de ses six sorties renvoient `{ sent: false }` sans exception (lignes 77, 128, 162,
168). Le `catch` ne se déclenche donc jamais pour un échec d'envoi. Mailjet non configuré,
identifiants refusés, expéditeur non validé, message rejeté ⇒ les erreurs sont marquées
« notifiées », le filtre `where: { notifiee: false }` (ligne 191) les exclut définitivement
des récapitulatifs suivants, et personne n'est prévenu.

**Aggravant, et c'est le vrai piège** : `suivi-erreurs.service.spec.ts` couvre le cas
d'échec — mais un cas qui ne peut pas se produire. Le mock renvoie `undefined` (ligne 50) au
lieu de `{ sent: true }`, et le seul test d'échec (lignes 244-250) utilise
`mockRejectedValueOnce`, une exception que le vrai service ne lève jamais. Le test est vert
et son intitulé affirme exactement la garantie qui n'existe pas.

Le bon patron est déjà écrit dans le dépôt :
`notification-supervision.service.ts:88-90` — *« Invariant 10 : c'est la valeur rendue qui
fait foi, jamais l'absence d'exception »* — et son commentaire d'en-tête désigne nommément
`SuiviErreursService` comme le dernier appelant fautif. **Corriger le test en même temps que
le code**, sinon la correction passera sans que rien ne le prouve.

### 3. `deployer.sh` applique la configuration Caddy avant de la valider

Confirmé : `grep -rn "caddy validate" deploy/` ne renvoie rien. Le déroulé est
`md5sum` hôte vs conteneur (`deployer.sh:146-149`) → `docker compose up -d --force-recreate
caddy` (`:153`) → comparaison d'empreintes après coup (`:158-163`) → sonde HTTP publique
(`:166-203`). Les deux contrôles sont **postérieurs** et aucun ne teste la syntaxe : un
`Caddyfile` invalide n'est détecté qu'après recréation, par un service déjà tombé — et
seulement si `FRONTEND_DOMAIN` est renseigné (sinon, ligne 91, simple avertissement et
contrôle sauté).

En revanche, le `--force-recreate` **n'est pas une négligence** : il est motivé lignes
130-145. Un bind mount de fichier attache l'inode ; `rsync` en crée un nouveau ; un `reload`
relit donc l'ancienne configuration en rapportant un succès. C'est la panne du 03/08/2026.
Le correctif à écrire est un `caddy validate` **avant** la recréation, pas un retour au
`reload`.

### 4. Deux copies d'anciens secrets en clair sur le poste

`backend/.env.avant-cle-dev` et `backend/.env.avant-cle-20260818-1444` (22 lignes chacune)
contiennent un ancien couple Mailjet (`MAILJET_API_SECRET` commençant par `eeb9…`, différent
de l'actuel) et un ancien `JWT_SECRET`. Elles sont gitignorées — rien n'a fuité — mais ce
sont des secrets révoqués laissés en clair, sans usage. **À supprimer.**

### 5. `.claude/settings.json` est suivi par git et absent des deux worktrees

C'est le seul fichier de configuration d'agent partagé du monorepo, et il n'est sur le
disque ni de `argon-mobility` ni de `argon-ci`. Soit il a été supprimé sans être décommité,
soit il n'a jamais été restauré. À trancher : le rétablir, ou le sortir du suivi.

### 6. Le dépôt vitrine n'avait aucune documentation d'amorçage — *corrigé aujourd'hui*

`CLAUDE.md` contenait **une ligne** (`@AGENTS.md`), `AGENTS.md` **uniquement** le bloc
auto-généré par `next dev`, et `README.md` le texte de `create-next-app` intact : mode
d'emploi de Vercel, mention de la police Geist que le site n'utilise pas. Une session
ouvrant ce dépôt n'apprenait rien.

Corrigé : `claude/etat-du-projet.md` (point d'entrée unique), `CLAUDE.md` réécrit,
